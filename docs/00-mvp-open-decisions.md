# Hotel Booking Platform — MVP-ийн нээлттэй шийдвэрийн нэгдсэн жагсаалт

**Хувилбар:** 1.0  
**Огноо:** 2026-08-25  
**Төлөв:** MVP Requirements Baseline 1.0 — кодын суурийн өмнөх P0 product/schema/API шийдвэр бүгд хаагдсан  
**Зорилго:** Ерөнхий баримт бичгийг эцэслэж, хөгжүүлэлт эхлэхээс өмнөх нээлттэй асуудал, гаднын хамаарал болон MVP-ээс хойшлуулсан ажлыг нэг газарт хянах

## 1. Ангиллын тайлбар

- **P0 — Кодын суурийн өмнө шийдэх:** Өгөгдлийн загвар, эрх, мөнгөний урсгал эсвэл үндсэн workflow-д шууд нөлөөлнө. Эдгээрийг батлаагүй байхад тухайн модулийг кодлохгүй.
- **P1 — MVP хүлээлгэн өгөхөөс өмнө шийдэх:** Түр default/config ашиглан хөгжүүлж болох боловч MVP-г бэлэн гэж үзэхээс өмнө батална.
- **EXT — Гаднын баталгаажуулалт:** Гэрээ, хууль, банк/provider эсвэл ЦЕГ-аас хамаарна. Mock/sandbox хөгжүүлэлтийг бүхэлд нь хориглохгүй боловч production ашиглалтад заавал хаана.
- **DEFER — MVP-ээс хойш:** Одоогийн MVP scope-д оруулахгүй гэж тодорхой тэмдэглэсэн ажил.

## 5. DEFER — MVP-ээс хойшлуулсан эсвэл оруулахгүй зүйл

- Restaurant-ийн нэмэлт нарийвчилсан дүрмүүдийг үндсэн order state дууссаны дараа тусдаа үе шатанд боловсруулна.
- Operation Dashboard-ийн автомат/хуваарьт SMS campaign болон two-way SMS inbox MVP-д орохгүй.
- Бүртгэлтэй email-д хандах боломжгүй hotel account recovery нь Operation Dashboard-ийн MVP функц биш; Platform Super Admin-ийн офлайн журам байна.
- Police Admin-ийн бүх hotel check-in жагсаалтыг Excel-ээр татах боломж MVP-д байхгүй гэж өмнө баталсан.
- Нэг өрөөнд үндсэн зочноос бусад хамт байрлагчийг тус бүрээр бүртгэхгүй.
- Restaurant хоолны төлбөрийг hotel checkout, барьцаа, Reception cash shift болон hotel room/minibar орлогод нэгтгэхгүй.
- Nightly stay-ийн optional early-morning/business-day cutoff current MVP-д орохгүй; бүх nightly check-in `STAY-DEC-007`-ын next-calendar-day дүрмийг ашиглана.
- Wanted case шинээр `ACTIVE` болоход зөвхөн тухайн мөчийн active stay-г шалгана; completed stay-д MVP retroactive scan хийхгүй (`POL-DEC-017`).

## 6. Баримт бичгийн consistency baseline

- Online booking shape/inventory нь `BK-DEC-012`–`014`; hold, callback, cancellation/no-show, commission/refund/settlement нь `PAY-DEC-005`–`009` гэсэн нэг source of truth-тэй.
- Restaurant fulfillment, payment, refund request болон handoff-ийг тусдаа state axis-аар хадгална (`REST-DEC-001`–`006`).
- Current room occupancy болон future reservation тусдаа derive хийгдэнэ; `Захиалгатай` гэдгийг current occupancy state болгон хадгалахгүй.
- Guest identity нь RC-DEC-044, Police Person–Case–Match нь POL-DEC-017–022, permission нь RBAC matrix-ийг дагана.
- Мөнгөн transition бүр immutable ledger/event, idempotency key, provider reference unique constraint болон authoritative server transaction ашиглана.
- Энэ аудитын дараа шийдэгдсэн scope-д мэдэгдэж буй schema/API зөрчил болон нээлттэй P0 үлдээгүй.

## 7. Баримт бичгийг “финал” болгох санал болгож буй дараалал

1. **P1 default:** UI/OTP/notification/retention/non-functional утгуудыг implementation config болон acceptance target болгох; эдгээр нь одоогийн schema суурийг дахин нээхгүй.
2. **EXT register:** owner, гэрээ/албан эх сурвалж, sandbox credential болон production exit criteria тогтоох.
3. Захиалагч `финал` гэж баталсны дараа architecture, database/API contract, development backlog руу шилжих.

## 8. Хөгжүүлэлт рүү шилжих gate

Product/schema/API-ийн P0 шийдвэр бүгд хаагдсан. Захиалагч `финал` гэж ил тод баталсны дараа энэ baseline-ийг input болгон architecture, database schema, API contract болон development backlog боловсруулна. P1 нь тохиргоо/acceptance, EXT нь sandbox/provider/legal/production release gate хэлбэрээр тусдаа хянагдана.
