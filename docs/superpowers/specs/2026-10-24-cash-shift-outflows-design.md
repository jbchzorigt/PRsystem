- **Огноо:** 2026-10-24
- **Төлөв:** Хэлэлцэж батласан (5 хэсэг), spec хянуулахаар

- **Шийдсэн нээлттэй асуудал:** D-03-ын касс (24)-ийн хэсгийг энэ шатанд онооно. C-053-ын safe, bank deposit, owner withdrawal, top-up, cash expense-ийн хэсэгчилсэн хамрах хүрээг тогтооно.

## 1. Зорилго

Ээлжийн зөрүү зөвхөн **жинхэнэ** дутагдал/илүүдлийг харуулдаг болох. Зочны бус шалтгаанаар (эзэн авах, жижиг худалдан авалт, банкинд тушаах, сейф рүү хийх) кассаас гарсан мөнгө бүр тухайн агшинд, хариуцагчтай, холбоостой хөдөлгөөнөөр бүртгэгдэнэ.

Одоо эдгээр урсгалын аль нь ч системд байхгүй тул эзэн 200,000₮ аваад гарахад ресепшний ээлж 200,000₮ дутагдалтай мэт хаагдана.

## 2. Гол загвар

**Б төрлийн буудал:** 20–60 өрөө, өдөр Manager байна, шөнө зөвхөн Reception ажиллана. Шөнө Manager/Admin байхгүй нөхцөлд урсгал бүр ажиллах ёстой.

Жижиг буудал (нэг хүн олон role) одоогийн нэг ажилтантай горим (SHIFT-DEC-003, 004) болон олон role-той account-аар дэмжигдэнэ. 24/7 duty manager-тэй буудалд Manager role тухайн үүргийг гүйцэтгэнэ; тусгай дүрэм шаардахгүй.

## 3. Хамрах хүрээ

### 3.1 Орно

- Мөнгөний байршлын төрөл: `DRAWER`, `SAFE`, `IN_TRANSIT` (§5).
- Жижиг зардал (petty cash) лимиттэй (§6.1).
- Эзэн/бусад хүнд мөнгө өгөх (§6.2).
- Банкинд тушаах "замд яваа мөнгө" урсгал (§6.3).
- Сейф: blind drop, дугтуй тоолох, сейфээс гаргах (§6.4).
- Касс нэмэх (top-up) (§6.5).
- Бусдын хийсэн хөдөлгөөнийг кассын эзэн тоолж хүлээн авах (§6.6).
- Лимитээс дээш зардал, нийлүүлэгчид бэлнээр төлөх (minibar stock receipt-тэй холбох) — Manager-ийн шууд төлөлт, Admin дараа нь хянана (§6.7).
- Ээлжийн хаалтын дутуу хэсэг: Manager-ийн "дахин тоолуулах", зөрүүний засвар, Admin-д дамжуулах босго, тайлан (§7).
- Эрх (§8), subscription lock үеийн дүрэм (§10).

## 5. Мөнгөний байршил ба хөдөлгөөн

### 5.1 Одоогийн бүтэц (кодоос)

- `cash_drawer` мөр бүр `shift_id NOT NULL`, `UNIQUE(tenant_id, shift_id)`-тэй (`001_cash.sql`).
- `cash_event.shift_id NOT NULL`; хөдөлгөөн нь signed `posted_delta` / `reserved_delta`.
- Хамгаалалт: `cash_book` root lock, `available = posted − reserved`, idempotency (`cash_receipt`), append-only journal, outbox.

### 5.2 Өөрчлөлт: `cash_drawer`-ийг ерөнхий байршил болгож өргөтгөнө

Шинэ хүснэгт нэмэхгүй. `cash_drawer`-т байршлын төрөл нэмж, ээлжийн шаардлагыг төрлөөс хамааруулна.

| Төрөл | Ээлж | Хариуцагч | Тоо |
| --- | --- | --- | --- |
| `DRAWER` | Заавал (одоогийнх шиг) | Идэвхтэй ээлжийн Reception | Олон |
| `SAFE` | Үгүй | Manager/Admin нээж тоолно | Буудалд 0 эсвэл 1 (CASH-DEC-002) |
| `IN_TRANSIT` | Үгүй | `holder_id` заавал | Банкинд тушаах бүрд нэг; дуусахад хаагдана |

`cash_event.shift_id` нь зөвхөн `DRAWER` байршлын хөдөлгөөнд заавал байна. Forward migration-аар өөрчилнө; өмнөх migration-уудыг засахгүй.

**Нийт бэлэн мөнгө** = бүх `DRAWER` + `SAFE` + нээлттэй `IN_TRANSIT`.

### 5.3 Шинэ хөдөлгөөний төрөл

Нэршил `docs/24` §5-тай яг ижил.

| Хөдөлгөөн | Чиглэл | Байршил | Холбоос |
| --- | --- | --- | --- |
| `CASH_TOP_UP` | IN | DRAWER | эх үүсвэр, шалтгаан |
| `PAID_CASH_EXPENSE` | OUT | DRAWER (§6.1, §6.7) эсвэл SAFE (§6.7) | expense бичлэг; inventory purchase бол minibar receipt |
| `OWNER_OTHER_WITHDRAWAL` | OUT | DRAWER эсвэл SAFE | withdrawal бичлэг |
| `SAFE_TRANSFER_OUT` / `SAFE_TRANSFER_IN` | хос | DRAWER ↔ SAFE | дугтуй эсвэл safe release |
| `TRANSIT_OUT` / `TRANSIT_IN` | хос | DRAWER/SAFE → IN_TRANSIT | bank deposit бичлэг |
| `BANK_DEPOSIT_OUT` | OUT | IN_TRANSIT | банкны баримтын дугаар |
| `CASH_CORRECTION_IN` / `CASH_CORRECTION_OUT` | IN/OUT | DRAWER | анхны shift ID |
| `COUNT_VARIANCE_IN` / `COUNT_VARIANCE_OUT` | IN/OUT | SAFE эсвэл IN_TRANSIT | дугтуй/transit, хариуцагч |

Хос хөдөлгөөн нэг transaction-д, нэг холбоос ID-тай бүртгэгдэнэ. Бүх хөдөлгөөнд дүн > 0 (signed delta нь чиглэлээс серверт тогтооно), actor, recorded_at, idempotency key байна.

Кодын хуучин нэрсийг өөрчлөхгүй; `docs/24`-т дараах хүснэгтийг нэмнэ.

| --- | --- |
| `INITIAL_FLOAT` | `INITIAL_FLOAT` |
| `GUEST_PAYMENT_RECEIVED` | `SERVICE_CASH_PAYMENT` |
| `GUEST_DEPOSIT_RECEIVED` | `DEPOSIT_CASH_RECEIPT` |
| `GUEST_REFUND_RESERVED` / `PAID` / `RELEASED` | `SERVICE_CASH_REFUND` эсвэл `DEPOSIT_CASH_REFUND`; `guest_refund.receipt_id` → `guest_receipt.purpose` (`PAYMENT`/`DEPOSIT`)-ээр ялгана. RESERVED/RELEASED нь reservation, posted биш |

## 6. Урсгалууд

### 6.1 Жижиг зардал (CASH-DEC-012)

**Тохиргоо (Hotel Admin):**
- нэг удаагийн лимит, анхдагч 50,000₮;
- нэг ээлжийн лимит, анхдагч 100,000₮ (ээлж бүрт шинээр тоологдоно);
- идэвхтэй ангиллын жагсаалт (`docs/23` §4.4-ийн default category-оос эхэлнэ).

**Бүртгэх (идэвхтэй ээлжтэй Reception):** дүн, ангилал, тайлбар, баримт (§6.8).

- Expense бичлэг `Paid` + `PAID_CASH_EXPENSE` нэг атомик transaction.
- Хяналтын төлөв: `Хянах хүлээгдэж буй` → `Зөвшөөрсөн` эсвэл `Маргаантай`.
- `Маргаантай` нь хөдөлгөөнийг буцаахгүй. Мөнгө буцаж кассанд орвол `CASH_CORRECTION_IN` анхны expense-тэй холбоостой бүртгэгдэнэ. Маргаантай зардал бүртгэсэн Reception-ий зөрүүний түүхэд тоологдоно.
- Нэг удаагийн эсвэл ээлжийн лимит давбал `PETTY_LIMIT_EXCEEDED` шалтгаантай хориглоно; дэлгэц Manager-ийн шууд зардал (§6.7) руу чиглүүлнэ.

### 6.2 Эзэн/бусад хүнд мөнгө өгөх (CASH-DEC-013)

| Бүртгэгч | Хүлээн авагч | Үр дүн |
| --- | --- | --- |
| Hotel Admin | Өөрөө эсвэл бусад | Шууд `Баталгаажсан`, self-approved audit |
| Manager/Manager Plus | Hotel Admin account эсвэл `Бусад хүн` (нэр + шалтгаан) | `Баталгаа хүлээж буй` |
| Reception | Зөвхөн буудлын Hotel Admin account | `Баталгаа хүлээж буй` |

- Мөнгө бүртгэсэн агшинд кассаас (эсвэл сейфээс) `OWNER_OTHER_WITHDRAWAL`-ээр хасагдана. Бусдын кассаас бол §6.6 үйлчилнэ.
- Хүлээн авагч Hotel Admin баталгаажуулна; `Бусад хүн` бол дурын Hotel Admin.
- 24 цагийн дотор баталгаажаагүй бол Hotel Admin-д сануулга.
- Татгалзвал хөдөлгөөн буцахгүй. Тухайн ээлжийн review `DISPUTED` + `ADMIN_REQUIRED` болно (§9).
- Expense биш (CASH-DEC-007). Нийлүүлэгчийн төлбөр, бараа/үйлчилгээний төлбөрийг withdrawal-ээр бүртгэхийг хориглоно: дэлгэц шалтгаан сонгох үед "Энэ нь зардал уу?" гэж §6.1/§6.7 руу чиглүүлнэ, Hotel Admin `Бусад хүн` withdrawal бүрийг хяналтын жагсаалтад тусад нь харна.

### 6.3 Банкинд тушаах (CASH-DEC-014)

1. **Эхлүүлэх** (Manager/Manager Plus/Hotel Admin): эх байршил (DRAWER эсвэл SAFE), дүн. Шинэ `IN_TRANSIT` байршил (holder = эхлүүлэгч) үүсэж `TRANSIT_OUT/IN` бүртгэгдэнэ. DRAWER-аас бол §6.6.
2. **Дуусгах** (зөвхөн holder): банкны баримтын дугаар, тушаасан дүн → `BANK_DEPOSIT_OUT`, байршил хаагдана.
3. Тушаасан ≠ авсан бол зөрүүг `COUNT_VARIANCE_OUT/IN`-ээр holder-ийн нэр дээр бүртгэж Hotel Admin хянана.
4. **Хугацаа:** эхлүүлснээс 48 цаг (Бямба, Ням гарагийг тооцохгүй) дотор дуусаагүй бол Hotel Admin-д сануулга. Баярын өдөр Admin сануулгыг тайлбартай хаах боломжтой.
5. Hotel Admin өөрөө эхлүүлж дуусгасан бол `self-reviewed`.
6. Expense биш.

### 6.4 Сейф (CASH-DEC-015)

- **Drop** (идэвхтэй ээлжтэй Reception, өөрийн кассаас): дүн + дугтуйны дугаар (буудал дотор давтагдахгүй) → `SAFE_TRANSFER_OUT/IN`, дугтуй `Битүүмжилсэн`. Өөрийн кассын хөдөлгөөн тул §6.6 шаардахгүй.
- **Нээж тоолох** (Manager/Manager Plus/Hotel Admin): битүүмжийн байдал (`Бүтэн` / `Гэмтсэн`) ба бодит дүн → дугтуй `Тоологдсон`.
  - Битүүмж бүтэн, зөрүүгүй бол тоологчоор хаагдана.
  - Битүүмж бүтэн, зөрүүтэй бол `COUNT_VARIANCE_IN/OUT` drop хийсэн Reception-ий нэр дээр бүртгэгдэж, дүнгээс үл хамааран Hotel Admin хянана. Reception өөрийн нэр дээрх зөрүүнд тайлбар бичнэ.
  - Битүүмж гэмтсэн бол (зөрүүтэй эсэхээс үл хамааран) `COUNT_VARIANCE` хариуцагчгүй (`Тодорхойгүй`) бүртгэгдэж, Hotel Admin хариуцагчийг шалтгаантай тогтооно эсвэл `Тодорхойгүй` хэвээр хаана. Тоологч заавал тайлбар бичнэ.
- **Тоолох хугацаа:** drop хийснээс 24 цагийн дотор тоологдоогүй дугтуй бүрийн талаар Hotel Admin-д сануулга очно.
- **Сейфээс гаргах** (Manager/Manager Plus/Hotel Admin): идэвхтэй ээлжтэй DRAWER руу (`SAFE_TRANSFER_OUT/IN`, §6.6) эсвэл `IN_TRANSIT` руу (§6.3).
- **Тайлан:** сейфийн үлдэгдлийг `тоологдсон` ба `битүүмжилсэн дугтуй`-гаар тусад нь.

### 6.5 Касс нэмэх

`docs/24` §9.5 хэвээр: Manager/Manager Plus/Hotel Admin, эх үүсвэр ба шалтгаан заавал, `CASH_TOP_UP`, revenue биш. §6.6 үйлчилнэ.

### 6.6 Кассын эзний баталгаа (CASH-DEC-016)

Reception-ий идэвхтэй кассанд **өөр хүн** хийсэн хөдөлгөөн (банк руу авах, Manager-ийн бүртгэсэн withdrawal, шууд зардал §6.7, top-up, сейфээс гаргах). Petty зардал зөвхөн өөрийн идэвхтэй кассаас бүртгэгддэг тул энд хамаарахгүй (§8):

1. Үүсгэсэн агшинд OUT бол дүн reservation болж түгжигдэнэ; IN бол pending байна.
2. Кассын идэвхтэй ээлжийн эзэн мөнгийг тоолж `Хүлээн авах` эсвэл `Татгалзах` (шалтгаантай).
3. Хүлээн авбал хөдөлгөөн posted болно. Татгалзвал reservation чөлөөлөгдөж хөдөлгөөн үүсэхгүй; үүсгэгч зөв дүнгээр дахин бүртгэнэ.
4. Нэг ажилтантай горимд өөрийн кассанд хийсэн хөдөлгөөнд шаардахгүй.
5. **Manager custody (`cash_custody` = `HELD`) үеийн касс:** custody үед `cash_drawer.shift_id` хаагдсан хуучин ээлж дээр үлддэг (`handover.py`), тул тухайн DRAWER-т шинэ хөдөлгөөн (§6.1–6.7) хийхгүй (`DRAWER_IN_CUSTODY`). Custody эзэмшигч мөнгийг одоогийн custody handover-оор хүлээлгэн өгөх, эсвэл Reception role-оор шинэ ээлж нээсний дараа хөдөлгөөн хийнэ.

### 6.7 Manager-ийн шууд зардал (CASH-DEC-018)

Нийлүүлэгчид хүргэлтээр нь бэлнээр төлөх (ус, ундаа, minibar бараа, угаалга) зэрэг petty лимитээс дээш зардал.

**Тохиргоо (Hotel Admin):** Manager/Manager Plus-ийн нэг удаагийн дээд хязгаар, анхдагч 500,000₮. Түүнээс дээш зардлыг Manager кассаас төлөх зам A3 хүртэл байхгүй (`DIRECT_EXPENSE_LIMIT_EXCEEDED`). Hotel Admin нь зардлыг батлах эрх бүхий этгээд тул түүнд дээд хязгаар үйлчлэхгүй; том зардлыг Hotel Admin өөрөө энэ урсгалаар бүртгэнэ.

**Бүртгэх (Manager/Manager Plus/Hotel Admin):** эх байршил (DRAWER эсвэл SAFE), дүн, expense type (`Inventory purchase` / `Operating expense`, `docs/23` §4.1), ангилал, нийлүүлэгчийн нэр, тайлбар, баримт (§6.8).

- `Paid` + `PAID_CASH_EXPENSE` нэг атомик transaction. Reception-ий кассаас бол §6.6 (Reception мөнгө гарахыг тоолж хүлээн авна).
- `Inventory purchase` бол тухайн minibar warehouse purchase receipt-ийг (`/minibar/products/{id}/receipts`) заавал сонгоно. Нэг receipt нэг л expense-тэй холбогдоно (FIN-DEC-004: давхар expense болохгүй). Receipt нь урьдчилан бүртгэгдсэн байх ёстой.
- Хяналт: `Хянах хүлээгдэж буй` → Hotel Admin `Зөвшөөрсөн` / `Маргаантай`. Hotel Admin өөрөө бүртгэсэн бол `self-reviewed`.
- `Маргаантай` нь §6.1-тэй ижил: хөдөлгөөн буцахгүй, буцаж орсон мөнгө `CASH_CORRECTION_IN`, бүртгэгчийн зөрүүний түүхэд тоологдоно.
- Reception энэ урсгалыг ашиглахгүй.

### 6.8 Баримт ба eBarimt (§6.1, §6.7)

Зардал бүрт баримтын төрөл заавал:

| Төрөл | Нэмэлт талбар |
| --- | --- |
| `eBarimt — байгууллагын ТТД-ээр` | eBarimt-ийн ДДТД |
| `eBarimt — хувь хүнээр` | eBarimt-ийн ДДТД, шалтгаан |
| `Цаасан/бусад баримт` | баримтын дугаар |
| `Баримтгүй` | шалтгаан |

Hotel Admin-ийн хяналтын жагсаалт ба тайланд `хувь хүнээр` болон `баримтгүй` зардлыг тусад нь харуулна (НӨАТ-ын хасалт авах боломжгүй).

## 7. Ээлжийн хаалт ба зөрүү

### 7.1 Хаалтын өмнөх шалгалт

| Хаалтыг хориглоно | Хориглохгүй, тайланд тусад нь |
| --- | --- |
| Pending drawer transfer (одоо бий) | Эзний баталгаа хүлээж буй withdrawal |
| Дуусаагүй QPay/картын гүйлгээ (одоо бий) | Хянагдаагүй зардал (§6.1, §6.7) |
| §6.6-ийн хүлээн аваагүй хөдөлгөөн (шинэ) | Нээлттэй `IN_TRANSIT` |

### 7.2 Харагдах төлөв (SHIFT-DEC-010)

Хадгалсан төлөв хэвээр: `reception_shift.state` (`OPEN`/`SUBMITTED`/`CLOSED`), `shift_handover.state` (`SUBMITTED`/`RETURNED`/`ACCEPTED`), `review_state`. Дэлгэцэнд `docs/03` §6.1-ийн нэрийг derive хийнэ. Хүснэгтийг дээрээс доош шалгаж, **эхний таарсан мөр**-ийг авна (жишээ нь self-close нь review-ээс үл хамааран "Өөрөө хаасан"; санхүүгийн review төлөв тусдаа badge-аар харагдана, SHIFT-DEC-001):

| Хадгалсан | Харагдах |
| --- | --- |
| shift `OPEN`, сүүлийн handover `RETURNED` (буцаалтын дараа шинэ handover илгээгээгүй) | Дахин тоолох шаардлагатай |
| shift `CLOSED`, касс `cash_custody` = `HELD` | Manager-ийн хадгалалтад (custody) |
| shift `OPEN` | Нээлттэй |
| shift `SUBMITTED`, handover `SUBMITTED` | Хүлээлгэн өгсөн |
| shift `CLOSED`, self-close биш, review `MANAGER_REQUIRED`/`ADMIN_REQUIRED`/`DISPUTED` | Мөнгө хүлээн авсан |
| shift `CLOSED`, self-close | Өөрөө хаасан |
| shift `CLOSED`, review `APPROVED`/`NOT_REQUIRED` | Хаагдсан |

### 7.3 Manager-ийн дахин тоолуулалт (SHIFT-DEC-009)

Handover `SUBMITTED` (хүлээн авагч баталгаажуулаагүй) үед Manager/Manager Plus (эсвэл орлож буй Hotel Admin) шалтгаантай `RETURNED` болгоно. Одоогийн хүлээн авагчийн буцаалттай ижил үр дагавартай.

### 7.4 Зөрүүг шийдвэрлэх

`CLOSED` ээлжийн зөрүүтэй review дээр:
- **Зөвшөөрөх:** шалтгаан заавал; зөрүү ээлжийн эзэмшигчийн нэр дээр үлдэнэ.
- **Засвар:** одоогийн идэвхтэй DRAWER-т `CASH_CORRECTION_IN/OUT`, анхны shift ID-тай, effective = бүртгэсэн агшин (CASH-DEC-009). Анхны expected/actual/opening өөрчлөгдөхгүй.

`DISPUTED` нь эдгээрийн аль нэгээр л `APPROVED` болно.

### 7.5 Admin-д дамжуулах (SHIFT-DEC-008)

`ADMIN_REQUIRED` болох нөхцөл:
- \|зөрүү\| > босго (Hotel Admin тохируулна, анхдагч 20,000₮; илүү/дутуу аль аль нь);
- тухайн ажилтанд сүүлийн 30 хоногт (буудлын цагийн бүсээр) тоологдох зөрүүтэй бүртгэл ≥ N (анхдагч 3). Тоололд ээлжийн зөрүү, өөрийн нэр дээрх `COUNT_VARIANCE` (дугтуй, transit), `Маргаантай` зардал (§6.1, §6.7) орно. Зөвхөн \|дүн\| ≥ тоолох доод хэмжээ (Hotel Admin тохируулна, анхдагч 1,000₮) зөрүүг тоолно; түүнээс бага зөрүү ердийн Manager review-ээр явах бөгөөд **автоматаар зөвшөөрөгдөхгүй**. Хариуцагч нь `Тодорхойгүй` `COUNT_VARIANCE` хэнд ч тоологдохгүй;
- одоогийн дүрэм: Manager тухайн ээлжид Reception байсан, зөрүүтэй self-close.

### 7.6 Тайлан

- Ээлжийн тайлан: шинэ хөдөлгөөнүүд төрлөөр; баталгаа хүлээж буй withdrawal, хянагдаагүй зардал тусдаа.
- Hotel Admin: self-close шүүлтүүр (REQ-03-08); ажилтан тус бүрийн 30 хоногийн зөрүүний түүх (export-тэй); нийт бэлэн мөнгө (касс + сейф (тоологдсон/битүүмжилсэн) + замд); 24 цагаас дээш тоологдоогүй дугтуй; `Бусад хүн` withdrawal; `хувь хүнээр`/`баримтгүй` зардал (§6.8).
- Manager: ажилтны зөрүүний түүх (export-гүй).
- Reception: зөвхөн өөрийн нэр дээрх зөрүү ба шийдвэрүүд.

## 9. Edge case

| Нөхцөл | Үйлдэл |
| --- | --- |
| Нэг кассанд зэрэг бүртгэл, давхар дарах | `cash_book` lock + idempotency; давхар хөдөлгөөн үүсэхгүй. Ижил key, өөр payload → conflict |
| available < дүн (pending transfer/reservation) үед зардал, drop, withdrawal, transit | Хориглоно (CASH-DEC-011) |
| §6.6-д кассын эзэн татгалзах | Хөдөлгөөн үүсэхгүй, reservation чөлөөлөгдөнө |
| Withdrawal татгалзсан, ээлжийн review аль хэдийн `APPROVED` | `APPROVED` → `DISPUTED` + `ADMIN_REQUIRED`. Энэ шилжилтийг зөвхөн энэ шалтгаанаар зөвшөөрнө |
| Давхардсан дугтуйн дугаар | Хориглоно |
| Сейфээс DRAWER руу гаргах, хүлээн авах кассанд идэвхтэй ээлж байхгүй | Хориглоно; `IN_TRANSIT` руу гаргах боломжтой |
| Банкинд авснаас илүү тушаасан | `COUNT_VARIANCE_IN`, Hotel Admin хянана |
| Сейф үүсгээгүй буудал | Safe drop, сейфийн UI харагдахгүй |
| Нэг ажилтантай горим | §6.6 шаардахгүй; хянах зүйлс Hotel Admin руу |
| 30 хоног, тайлангийн өдөр | `Asia/Ulaanbaatar` |
| Ээлж хаагдсан, ресепшн гарсан хойно дугтуйн зөрүү илэрсэн | Битүүмж бүтэн бол `COUNT_VARIANCE` drop хийсэн хүний нэр дээр, гэмтсэн бол `Тодорхойгүй`; хаагдсан ээлжийг өөрчлөхгүй |
| Manager custody-тай касст зардал, withdrawal, transit, top-up | Хориглоно (`DRAWER_IN_CUSTODY`, §6.6 алхам 5) |
| Inventory purchase зардал receipt-гүй, эсвэл receipt аль хэдийн өөр expense-тэй холбогдсон | Хориглоно (FIN-DEC-004) |
| Manager-ийн шууд зардал дээд хязгаараас давсан | Хориглоно (`DIRECT_EXPENSE_LIMIT_EXCEEDED`); Hotel Admin өөрөө бүртгэх эсвэл A3 |

## 11. Тест ба хүлээлгэн өгөх

- Урсгал бүрийг TDD (red → green → refactor).
- PostgreSQL integration: атомик хос хөдөлгөөн, RLS tenant тусгаарлалт, idempotency/replay, immutable trigger, reservation invariant, §9-ийн мөр бүр.
- Domain тест: petty лимит ба Manager-ийн дээд хязгаар, Admin-д дамжуулах тоолол (30 хоног, timezone, тоолох доод хэмжээ, `Тодорхойгүй` хасагдах), харагдах төлөвийн derivation (§7.2 хүснэгт бүрэн), eBarimt төрлийн заавал талбарууд (§6.8).
- PostgreSQL: inventory purchase receipt ↔ expense 1:1 constraint; custody касст хөдөлгөөн хориглох; дугтуйн битүүмжийн төлөв ба хариуцагчийн дүрэм.
- Browser suite: Reception (petty, withdrawal, drop, §6.6), Manager (шууд зардал, transit, дугтуй, дахин тоолуулах, review), Hotel Admin (тохиргоо, хяналт, тайлан).
- Хүлээлгэн өгөх нөхцөл: `python -m scripts.run_postgres_shard` 4 shard 0 skip; бүх browser suite; `tests/browser/validate_requests.py`; design/token check.
- Хэрэглээний туршилт (`scripts.ui_review`): "шөнийн ээлж: drop + petty зардал → өглөөний хүлээлцэлт → нийлүүлэгчид бэлнээр төлөх → дугтуй тоолох → Manager банк руу → эзэн мөнгө авах → Admin хяналт" сценарийг бодит Reception, Manager хүнээр туршиж, `docs/76`-ийн ажиглалтын хүснэгтэд бүртгэнэ.
